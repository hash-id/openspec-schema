# Research: hard session separation between planning (discovery→align) and `apply`

**Date:** 2026-08-03
**Scope:** the hash schema's `apply` phase instruction (top-level `apply` block in `openspec/schemas/hash/schema.yaml`) currently reads discovery.md, proposal.md, specs/**/*.md, and design.md "as needed," with no stated priority, and no requirement that `apply` runs in a different session from the one that produced align.md. An initial research pass (§1-3 below) explored promoting `align.md` to primary carry-forward context within a continued session (a compaction/prioritization framing). The user rejected that framing: the preference is a genuinely fresh session between `align` and `apply` — planning and implementation kept out of the same context window entirely, not summarized within one. §4-6 supersede §3's recommendation with research targeted at that stronger requirement, including whether an agent can self-detect it's still in a stale (continued) session and refuse to proceed.
**Status:** research and synthesis complete. No changes made to `schema.yaml` yet — findings and recommendation only, pending an adoption decision. §3's original recommendation is retained below for record but is **superseded** by §6.
**Sources:** 8 for the original compaction-framing pass (§2), 9 for the fresh-session/self-detection pass (§5).

## 1. Summary (original compaction framing)

Anthropic's context-engineering guidance (source 1) frames context as a finite "attention budget" subject to "context rot" — degraded recall/reasoning as context grows, as a gradient rather than a cliff, present in all models. Their prescribed mitigations for long-horizon tasks are compaction (summarize history into a condensed artifact, then reinitiate from the summary), note-taking (persistent files like NOTES.md reloaded at later points — "persistent memory with minimal overhead"), and sub-agent isolation. They also describe progressive/structured retrieval: load a lean, high-signal artifact up front, explore further only just-in-time, rather than loading everything with equal weight.

Anthropic's multi-agent research system writeup (source 2) gives direct precedent for treating a persisted summary as the authoritative checkpoint at a boundary: subagents pass lightweight references back rather than full context, and the lead agent explicitly saves its plan to memory before hitting context limits, retrieving that saved plan afterward rather than losing prior work.

An empirical paper on context rot in long-horizon search (source 3) shows this isn't just an efficiency concern: accuracy drops as trajectory length grows even when the context window has capacity to spare — a reasoning-degradation effect, not merely a truncation problem. Their best mitigation (periodic rewrite into a compact summary, discarding older raw output) beat keeping full raw history.

OpenAI's context-engineering cookbook pattern (source 4) adds a concrete mechanism this repo lacks: an explicit precedence hierarchy for resolving conflicts between context sources (current input overrides session memory, session memory overrides global memory), plus a strict "no invention" rule during summarization — because the consolidation step is "the most sensitive and error-prone stage," where a hallucination can propagate forward.

A tiered-memory architecture paper (source 5) formalizes the "consult the summary first, escalate only when insufficient" policy directly: a fast summary tier answers by default, escalating to an immutable raw-log tier only when a sufficiency check judges the summary insufficient — with verified findings written back into the summary tier linked to provenance. This suggests align.md entries should retain pointers back to the originating document/section, so `apply` can jump to the precise passage on escalation rather than re-reading whole files.

Anthropic's Agent Skills progressive-disclosure design (source 6) and their "new rules of context engineering" post (source 7) both corroborate that ordering of context loading is a deliberately designed property in current practice — not something left as an emergent "read as needed."

A supporting source on multi-agent handoffs (source 8) reinforces the caution side: handoffs should carry typed state/summaries as the default payload, with full context available only on request, but warns that "even minor hallucinations in a summary can propagate forward, contaminating future context" — relevant because this recommendation is only as safe as align.md's own fidelity.

align.md is a stronger candidate for this authoritative role than a generic auto-summary would be: unlike an LLM-generated compaction summary produced without human involvement, align.md is already an accumulated, severity-tagged, explicitly human-reviewed decision log (per `hrt-align-consistency-review/SKILL.md`'s WALKTHROUGH step) — closer to OpenAI's "no invention" bar than a typical summary artifact.

## 3. Original recommendation — superseded

Add explicit read-order and precedence language to the top-level `apply` block's instruction in `schema.yaml`:

> Before starting each task, read `align.md` first — it is the authoritative, decision-focused summary of everything resolved during discovery through align, including reasons for deferred items. Treat its findings and recorded decisions as binding. Consult `discovery.md`, `proposal.md`, `specs/**/*.md`, and `design.md` only to fill gaps align.md doesn't cover (e.g., detailed acceptance criteria, full rationale, or design specifics align.md only references). If align.md and an original document conflict, align.md wins — it reflects the latest reviewed and accepted state.

**This is superseded by §6.** The user's actual preference is stronger than reprioritizing which document to read within a continued session: planning and implementation should not share a context window at all. §1-3's compaction framing assumed continuity was a given and tried to manage it; §4-6 instead treat continuity itself as the thing to eliminate.

## 4. Revised scope: hard session separation, not compaction

The requirement: `apply` should run in a genuinely new session, not a continuation of whatever session produced align.md — keeping the long, exploratory planning conversation (dead ends, rejected drafts, back-and-forth) out of the implementation context entirely, rather than summarizing it. Beyond an instruction asking for this, the question is whether the agent can detect *from inside its own context* that it's still in the old, stale session, and refuse to proceed until a new one starts.

This runs into a hard architectural limit, confirmed independently by every source found on the point (§5, source 9): an LLM has no introspective access to "which session/conversation instance am I" — a transformer call is stateless, and nothing about session identity is available to the model except what happens to be sitting in its context window. So a refusal check cannot be "am I in the old session" (unanswerable) — it can only be "does my context currently contain specific content that would only be present if this were a continuation" (answerable, indirect, and imperfect).

## 5. Sources (session-boundary enforcement, 1–9)

1. **Will Ness — "Why You Need To Clear Your Coding Agent's Context Window"**. [willness.dev/blog/one-session-per-task](https://willness.dev/blog/one-session-per-task). Prescribes "one task, one session, clear between tasks," with concrete Claude Code `/clear` guidance and a "quality zone" heuristic (agents stay sharp under ~40% context use, degrade past ~70%). Puts the burden entirely on the user/operator to clear manually — no self-detection mechanism proposed.
2. **Ken Muse — "Why Focused AI Agents Get Better Coding Results"**. [kenmuse.com/blog/why-focused-ai-agents-get-better-coding-results](https://www.kenmuse.com/blog/why-focused-ai-agents-get-better-coding-results/). Describes a planner/coder split architecturally close to this schema's align→apply boundary: the planning agent produces a plan then "eliminat[es] all other context," and "a coding agent starts fresh with just the plan, the tools it needs, and the few files it needs to modify."
3. **Depot.dev — "Context isolation in coding agent loops"**. [depot.dev/blog/context-isolation-in-coding-agent-loops](https://depot.dev/blog/context-isolation-in-coding-agent-loops). Coins the description of a long single-session transcript as a "junk drawer" where load-bearing content becomes indistinguishable from noise; argues the fix is architectural subagent/session splitting, not mid-session cleanup.
4. **Augment Code — "Adversarial Code Review: Why the Maker Shouldn't Grade the Checker"**. [augmentcode.com/guides/adversarial-code-review](https://www.augmentcode.com/guides/adversarial-code-review). States plainly that "prompt engineering does not repair" self-review bias, citing research that masking a judge's ability to *recognize* its own output reduces self-preference more effectively than instructions telling it not to be biased — recognition, not instruction, drives the bias. Its own enforcement stack is architectural: fresh context window with only the diff, read-only permission boundary, different model, separate session/credentials. Directly relevant: this is the closest precedent to "instruction alone is known to underperform architectural separation."
5. **Cursor Community Forum — "Build the plan in a fresh context"**. [forum.cursor.com/t/build-the-plan-in-a-fresh-context/158649](https://forum.cursor.com/t/build-the-plan-in-a-fresh-context/158649). Live feature request from real users hitting exactly this pain point: *"to avoid context contamination, I have to manually save the plan and start a new session each time, which is quite cumbersome."* Notes OpenAI Codex CLI already ships "Plan Mode can start implementation in a fresh context" with a context-usage preview — evidence the industry is moving this into tooling (a CLI/UI feature), not agent self-enforcement.
6. **GitHub Spec Kit**. [github.com/github/spec-kit](https://github.com/github/spec-kit). Useful negative finding: its `spec → plan → tasks → implement` pipeline uses persisted files as the phase interface (the same pattern this schema's align.md/tasks.md already follows) but documents **no requirement or instruction to start a new session/chat between `/tasks` and `/implement`**. Even a prominent, credible spec-driven tool stops short of a hard session-freshness gate.
7. **Anthropic — "Building Effective AI Agents"**, and the multi-agent research system post via **Simon Willison's summary**. [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents), [simonwillison.net/2025/Jun/14/multi-agent-research-system](https://simonwillison.net/2025/Jun/14/multi-agent-research-system/). Isolation here is always architectural: "each subagent gets a self-contained task description... and a fresh context window. It doesn't know the other subagents exist" — granted by the orchestrator spawning a genuinely new agent, never something a single continuing agent decides to impose on itself.
8. **Anthropic — "Effective context engineering for AI agents"**. [anthropic.com/engineering/effective-context-engineering-for-ai-agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Explicitly contrasts compaction (same session, summarized) against sub-agent architectures (genuinely clean context windows) as the two available levers for long-horizon tasks — but never describes an agent instructed to self-isolate from its own prior context within one continuous session as equivalent to true sub-agent isolation.
9. **Atlan — "Why AI Agents Forget: The Stateless LLM Problem"**, corroborated by LessWrong/EA Forum summaries of Robert Long's work on LLM introspection. [atlan.com/know/why-ai-agents-forget](https://atlan.com/know/why-ai-agents-forget/). States the architectural fact directly: a transformer call is stateless; nothing persists after the call completes; a model cannot distinguish session continuity from its own weights or computation alone. Confirms any self-check must be content-based (what's visible in-context), never identity-based (which session this is) — there is no such signal available to check.

## 6. Recommendation (supersedes §3)

Two-layer design, since the evidence shows instruction-only fixes are known to underperform architectural ones (source 4), and true self-detection is architecturally impossible (source 9):

**Layer 1 — name the requirement plainly.** State in the `apply` instruction that it must run in a new session, not a continuation of the discovery-through-align conversation, and why (keep planning noise — dead ends, rejected drafts, back-and-forth — out of the implementation context).

**Layer 2 — a content-based tripwire, framed explicitly as best-effort.** Since the agent cannot know which session it's in, give it a checklist of content signals that indicate continuation, not session identity:

> Before starting Phase 1, check whether this conversation is a fresh session or a continuation of the discovery-through-align planning work. Signals that you are in a STALE (continued) session — if ANY are true, stop and tell the user to start a new session, passing only align.md and tasks.md as input:
> - You can recall specific back-and-forth from the discovery/proposal/align conversation that is not written down in align.md or tasks.md themselves (a rejected draft, a question the user answered verbally, an intermediate design you proposed and abandoned).
> - Your context contains the raw discovery interview transcript, or earlier superseded revisions of proposal.md, specs.md, or design.md.
> - You authored align.md in this same conversation.
>
> This check is necessarily imperfect — you have no way to know which conversation instance you are in, only what is visible in your context. Treat it as a best-effort tripwire, not a guarantee: an actual new session is the only real enforcement. If none of the above signals are present, proceed with Phase 1.

Reasoning tied to sources:
- The checklist is deliberately about **content sitting in context**, never "which session am I" — the only question an LLM can actually answer, per source 9.
- Framing it explicitly as "best-effort, not a guarantee" follows directly from source 4's finding that prompt-engineering-only fixes are known to underperform architectural separation for the closely analogous self-review-bias problem — the instruction should not overstate what it can deliver.
- Sources 1-3 and 5 confirm this is a real, actively-felt pain point across multiple tools/communities (Claude Code, Cursor, Codex), with the field's actual fix trending toward tooling-level support (a CLI/UI flag), not prose — worth flagging as a forward-looking note: if OpenSpec CLI or Claude Code ever exposes a hook/flag for "require a new session before this command," that is the correct place to enforce this, not `schema.yaml` prose. `schema.yaml` prose is the best available lever today, not the ideal one.
- Source 6 (spec-kit) shows this schema would be going further than existing prominent spec-driven tools on this specific point — worth being aware it's a deliberate, above-baseline choice, not catching up to an established norm.
