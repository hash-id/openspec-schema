# Design decisions and measured history

The rules in [AGENTS.md](../AGENTS.md) are terse on purpose. This file holds the *why* behind them: the rationale, the incidents, and the measurements. Each section links to its research doc under [docs/research/](research/). Read the relevant section before proposing to change a rule. Where this file mentions case counts, file sizes, or skill counts, they are orientation only — the code and its tests are the source of truth.

## 1. Pipeline shape: one path, graduated depth

- `proposal` is the only intent document. There is no `discovery` phase or file — removed in v15 (see `research/2026-10-21-tempa-spec-weight-and-phase-reduction.md`, summary in `research/2026-10-21-tempa-spec-weight-summary.md`). With `discovery.md` gone, nothing written exists for a model reviewer to check the proposal against, which is why `proposal` has no model review: `hrt-artifact-lint --phase=proposal` (structure, plus WARN-only size and shape rules) and the user's read-and-confirm replace it.
- The change-size rule in `proposal` ("two or more independent, separately shippable slices → ask once, default one change, defer under `## Out of Scope`") deliberately has **no size threshold**: a large change whose parts depend on each other is one change. There is no `openspec/BACKLOG.md`. Graduated depth inside the fixed phases — thin `design.md` → Destructive Critic only, `align` VERIFY only on a raised HIGH — is the schema's answer to "small changes pay too much": phases are never skipped, so scenario→task coverage is always checked by the lint. (2026-11 external review revisit: a size-gated "light path" was proposed and rejected — the light/heavy judgment cannot be made deterministically before a diff exists, and a self-classified light path is exactly where a spec-triggering change would escape verification.)
- `align` VERIFY running only when ALIGN raised a HIGH is measured: it skips 3 of 8 productive runs, accepted (`research/2026-08-03-deterministic-grounding-align-review.md`). The human gate in `align` itself: `research/2026-07-16-align-phase-human-review-gate.md`.
- `design.md` is mandatory for every change because optionality failed in practice: an agent once skipped it on a callable-code change and left `apply`'s seam override with nothing to read. The file always exists; only its depth scales with the change.

## 2. Adversarial review, seams, and the consequence gate

- `design.md`'s `## Shape / Seams` and the seam rule (highest available entry point, fewest seams, ideal one) come from `research/2026-08-27-mattpocock-skills-gate-and-seams.md`; `align`'s `specs <-> design` dimension enforces that every scenario has one, and `hrt-adversarial-authoring`'s `design` pass reviews them against `to-spec`'s rule.
- The adversarial pattern's origins: `research/2026-07-19-adversarial-4-agent-authoring.md`; judge bias and collusion risks: `research/2026-08-03-judge-bias-collusion-adversarial-authoring.md`; LLM-as-judge reliability generally: `research/2026-09-07-llm-as-judge-reliability-2026.md`.
- The **consequence gate** (a finding is actionable only if it names what a reader or implementer concretely hits when it's unfixed; "defer it / accept the drift" is not an alternative; never auto-resolve with a clean fix in hand) and the digest model come from `research/2026-09-09-technical-writing-adversarial-drafting-skills.md`.
- Review prompts are digests, not per-item questions (`hrt-adversarial-authoring` step 4, `hrt-align-consistency-review` step 8, `hrt-apply-code-review` step 8): actionable findings are shown together and answered one by one ("ok" never covers it); everything else is one digest "ok" accepts, at most 5 LOW findings shown.

## 3. Elephant-Goldfish Model (EGM)

Two rules from the EGM hold in all three review skills — evidence in `research/2026-11-16-egm-adoption-analysis.md` §3.1 and §3.2, model in `research/2026-11-16-elephant-goldfish-model.md`, source papers as PDFs in `docs/`:

1. A reviewer subagent that fails, times out, returns nothing, or cannot read an input is retried once, then recorded as `not run`. `not run` is never a clean review and blocks (artifact not finalized; `align` stops before WALKTHROUGH; `apply`'s 3rd pass `not run` = RELEASE BLOCKER).
2. A host where no subagent can be spawned is the same case: the skill stops and reports instead of asking whether to continue or reviewing in the same context.

Plus the rejection rule: a recommendation to reject a finding must name the file and line/section where the user can check the reason, or be labelled `unchecked reason:` in the digest (no extra question to the user).

## 4. tasks.md graph: `Depends on:` and parallel apply

- `Depends on:` became required in v19 because optionality failed: before v19 the line was optional and the `tasks` instruction said most changes need none, and only 4 of 25 changes wrote it. Required so each edge is a decision someone checked. There is deliberately **no `Touches:` or `Test:` line** — the declared dependencies are the only isolation, `align`'s `tasks graph` dimension checks they are true (an edge with no real need is LOW), and `apply` watches for the failure a missing edge causes (two concurrent groups changing the same file, or a test failing in code the group did not change).
- Parallel apply is declared in `tasks.md`, not decided at apply time. Concurrency limit `min(floor(cores / 3), floor(available GB / 2))`, in order when that is below 2 or unreadable. Scheduling is a rolling frontier (from mattpocock's `implement-spec`), one shared working tree, no worktrees, only the orchestrator ticks checkboxes, full suite only at quiet points. `apply` follows mattpocock's `implement` (not `implement-spec`): groups run in one context in order; no worktrees, per-ticket commits, or merger subagent. **Worktrees were rejected because each needs its own test environment** — for Odoo, one Odoo container and one database copy per worktree, which a typical laptop cannot carry; shared-tree parallel has the same limit when tests share one live database, which is why parallel stays a user choice. Prefactoring (from `to-tickets`) is a `tasks` exception: the `design` Decision records it, `tasks` makes it an early group; the limit formula lives only in the `apply` instruction. Evidence: `research/2026-11-20-apply-parallelism-and-mattpocock-implement.md`.

## 5. plain-language-writing

Pointed to *from inside* other instructions and skills, at whichever specific line produces user-facing text or artifact prose, because those points are scattered across `schema.yaml`, `hrt-align-consistency-review`, and `hrt-adversarial-authoring` — no phase owns them. It is a full skill of its own rather than a shared reference file because **skills cannot reliably reference files inside another skill's folder once installed** (no cross-skill path guarantee). Its two rule sets (COMMS vs. ARTIFACT) and the evidence: `research/2026-08-07-plain-language-non-native-readers.md`.

## 6. Skills as vendored dependencies

- Before vendoring, the installer made **four `npx skills add` calls — four network clones** — with a hard dependency on three third-party repos staying reachable (`mattpocock/skills`, `wshobson/agents`, `blader/humanizer`; the `wshobson/agents` skills have since been replaced by `hrt-security-pass`, and `humanizer` was dropped in v15: no evidence behind it, 30 KB). Vendoring collapsed that to one call and removed the outage risk (a third-party repo rename would break installs). Plan: `research/2026-07-16-skills-as-dependencies-plan.md`; the dependency model generally: `research/2026-07-16-skills-agents-as-dependencies.md`.
- The lone upstream still vendored, `mattpocock/skills`, is MIT; each vendored folder keeps the source `LICENSE` plus a generated `VENDOR.md` (source path + pinned commit).
- **`--full-depth` is required** on `npx skills add ${REPO}/skills`: the default walk stops at `skills/hrt-*/` and silently skips `skills/vendor/*`, and the installer's "Installed skills" echo is a fixed string that wouldn't reveal the gap. Verified end-to-end against a local clone: all vendored skills, bundled files included, land flat in `.agents/skills/<name>/`.
- `proposal` points at `grilling` directly, not `grill-me`: `grill-me` is a dead-end pointer (`disable-model-invocation: true`; its `SKILL.md` just says "run a `/grilling` session"), so an agent can never self-invoke it. Before vendoring any new external skill, check its `SKILL.md` for `disable-model-invocation` or a same-repo delegate target before assuming the name alone works from an instruction.

## 7. hrt-security-pass

Replaced three vendored `wshobson/agents` skills — about 8 KB of `SKILL.md` plus 64 KB of Python-dataclass references that added no knowledge a model lacks. OWASP ASVS was evaluated and deliberately **not** adopted: web-application-centred, no L1 requirements in V16 (logging and error handling), CC BY-SA 4.0, and a lookup script plus attribution is more machinery than a plan-time check needs. The skill is deliberately tiny (a gate plus a pointer, so a change touching no boundary pays almost nothing); `references/` files load on demand per touched surface. Evidence and sources: `research/2026-10-15-security-approach-vendored-skills-vs-standards.md`.

Reference-file format constraints (a maintenance contract, see AGENTS.md): official titles quoted only, no pasted prose from OWASP/MITRE, no invented titles, `agentic-top10-2026.md` stays flagged because the official page does not list the titles, the CWE file keeps MITRE's copyright and licence sentence (a condition of reuse), every question written for this skill, no framework file without checking it against that framework's own docs, `business-flow.md` quotes only WSTG v4.2 §4.10 titles (the page is "all rights reserved") with our own questions.

## 8. opengrep: required, no waiver

- Why required: on `sip` the scan found **about twenty SQL interpolations that the Semgrep registry packs did not** (`research/2026-10-25-sast-and-security-skills-landscape-evaluation.md` §4.2). It is protection with demonstrated unique yield, and a waivable check is a check that stops running — the same failure mode `floor-guard.cjs` exists to catch. The binary is a one-time-per-machine install, caught at `apply` PREFLIGHT before any code is written; dark mode does not route the rule to a decision gate because an autonomous agent would always waive.
- Why results stay "candidates" rather than automatic HIGH: the rules have not been measured on enough real code. A candidate is kept only if the changed code is exploitable and dismissed only with a one-line reason. (2026-11 external review suggested recording candidate counts per run to build that measurement; rejected: waivers; accepted and implemented: each pass's review report carries the tally — candidates raised, kept, dismissed — and the orchestrator records it in `apply-log.md`.)
- The `--baseline-commit` flag is banned: on opengrep 1.11.1 and 1.32.0 it **silently skips unstaged edits and untracked files**, and the review runs before anything is committed — so the scan runs on tracked files that differ from the base branch plus untracked ones. Pinned as a KNOWN GAP test so a fixed opengrep makes it fail and prompts a second look.
- The rules are local files (`hrt-security-pass/opengrep/`), so no registry is contacted; fixtures in `scripts/fixtures/opengrep-rules/`; `scripts/opengrep-rules.test.cjs` requires a positive and a negative case per rule; its engine tests skip when opengrep is not installed, so run `npm test` with opengrep on the machine before releasing a rule change. Rule tests passed on opengrep 1.11.1 and 1.32.0.

## 9. floor-guard.cjs

Adapted from `addyosmani/agent-skills`' floor guard (MIT, credited in the script header). It only flags; the reviewer classifies each flag in step 5; it is not a linter (exit 1 never blocks the loop by itself), and an answer the user already gave is not asked again on a later pass. The **change-wide assertion counting** and the **new-file skip exemption** come from a measurement on three downstream repositories: 18 of 18 per-file assertion drops were moves, rewrites, or spec changes; the one real weakening was blanket `@ts-ignore` in tests. Patterns cover Python (including unittest and Odoo) and JS/TS only — add an ecosystem after a real incident, not before. The `[security]` mutation probe was designed and deferred until a weak security test is seen in practice. Evidence and decisions: `research/2026-10-25-addyosmani-agent-skills-evaluation.md`.

## 10. hrt-mr-brief

`apply` Phase 3, adapted from `mattpocock/skills`' `pr` (itself credited to Dex Horthy's `show-me`) but local rather than vendored: the output is a file (`mr-brief.md`, Summary / Evidence / Merge Danger, next to `tasks.md`), not a PR body, and every section is sourced from the change's own artifacts and test runs. Kept schema-generic: headings in English, prose follows `proposal.md`'s language, no downstream team or tooling named; only generic paste-safety rules (no secrets or personal data, no closing keywords, no line starting with `/`). `apply` itself never commits, pushes, or touches the review system. `apply` Phase 1 keeps each task's RED output (`red-log.md`) so Evidence can quote it; like `red-log.md`, nothing lints `apply-log.md` or `mr-brief.md`.

## 12. Installer: steps and history

- Steps: clone `master` into a temp dir; copy **only** `schema.yaml` and `templates/*` (never `cp -r` the whole clone — the `npx skills add` call does its own independent clone and is not part of that invariant); provision skills via the single `npx skills add ${REPO}/skills --full-depth` call; write `./openspec/config.yaml`'s `schema:` and `context:` via `scripts/merge-config.cjs`. A failed skill install stops the installer (same as a failed schema clone) — skills aren't optional for a schema whose instructions point at them.
- Why `context:` exists at all: OpenSpec's CLI-injected-into-every-phase mechanism (confirmed against `Fission-AI/OpenSpec` issue #1524 — project-level `context` in `config.yaml` is "reliably applied" by the CLI to all artifact instruction generation, unlike agent-read files). Repo-wide MUSTs that apply to every phase belong there, written once by the installer, instead of duplicated into each `instruction:` block — YAML anchors/aliases can't substitute mid-paragraph inside a block-scalar `instruction: |` string (verified: an alias placed inside `|` text stays literal; it only expands as a whole-node value), so per-instruction duplication was the only in-file alternative. There is no CLI subcommand for writing `context:` (checked `openspec config` — it only touches the global `~/.config/openspec/config.json`, not the project `config.yaml`), hence the hand-rolled merge script.
- `merge-config.cjs` does a real YAML parse/modify/write (throwaway `npm install --no-save yaml`) rather than line-based text editing, so an existing `context:` that's multiline, block-scalar, or a commented-out sample survives instead of being clobbered.
- Two copies (bash + PowerShell) exist because the audience spans both; same steps, same order, same messages. Test the installer in a scratch dir — it writes to `./openspec/` (and `.agents/skills/`) relative to wherever it's run.

## 13. merge-config.cjs hardening story

Three subagents (one per angle — YAML data-shape, filesystem/OS, CLI-argument/adversarial) were run against the script to find edge cases beyond manual review. Their findings became most of the 37 `merge-config.test.cjs` cases, plus four real bugs, all now fixed (see the `FIXED:` convention below):

1. **Marker-version-drift** (real, happened once): the old `.includes(marker)` idempotency check couldn't tell "already merged" from "not yet merged", so a reworded marker in a future installer would append a second, possibly-contradictory block forever. Fixed by `replaceOrAppendBlock()`: exact, line-anchored marker match; everything from that line through the next blank line (or end of string) is replaced wholesale; otherwise append.
2. **Marker-as-substring false-positive idempotency**: a marker (or near-empty one) inside unrelated prose made the script treat the file as already merged and skip the real append, silently. Fixed by the same line-anchored match.
3. **Symlinked `configPath` was followed and written through.** Fixed: `fs.lstatSync` (not `fs.existsSync`, which follows symlinks and reports `false` for dangling ones, hiding them) before anything touches the path; any symlink refused with a clean error.
4. **Filesystem errors surfaced as raw stack traces** instead of the script's clean one-line style. Fixed: `readFileSync`/`mkdirSync`/`writeFileSync` wrapped; `failWithCleanFsError()` maps `EISDIR`, `EACCES`, `EPERM`, `ENOSPC`, `ENOTDIR` to one line.

**KNOWN LIMITATION** (deliberate, documented in the code comment above `replaceOrAppendBlock()` and its own test): block-end is inferred from the first blank line after the marker, so a `contextText` with an internal blank line only gets its first paragraph replaced on a reword — later paragraphs survive as orphaned trailing text. Not a real risk today (the installer's `CONTEXT_TEXT` is always a single line); a real fix needs an explicit block-closing delimiter, which would change the format of every already-installed `config.yaml` to solve a problem that doesn't exist yet.

Refused cleanly by design (non-zero exit, file untouched, no raw stack trace): `context:` as a non-string YAML node, malformed YAML (duplicate keys, tab indentation, multi-document stream) via `doc.errors`, a symlinked `configPath`, and filesystem errors.

## 14. Test suites: what they cover and the conventions

All run together: `cd scripts && npm install && npm test` (`node --test merge-config.test.cjs lint.test.cjs vendor-skills.test.cjs floor-guard.test.cjs`). The test files themselves are the source of truth for case lists — the counts here are orientation, not a checklist, and will drift by design:

- `lint.test.cjs` — 67 cases: hashtag counts, scenario-as-bullet, requirement with no scenario, missing WHEN/THEN, SHALL/MUST as WARN, unknown delta header, REMOVED without Reason/Migration, capability↔spec-file both directions, non-kebab capability, design.md sections, `Covers:` targets, "no new code surface" skip, archive tasks, non-checkbox bullets, External Dependencies rows, missing proposal sections, `--phase=proposal` + bad flags, plus suites for the tasks graph (`Depends on`), the security gate (keywords vs `[Threat`/skip line), task coverage (both directions, semicolons, case-insensitivity, HTML-comment lines ignored), threat ids (unique, covered, `[security]` task), proposal size/shape (word ceiling, comments excluded, fences, ≤5 open questions, `Size facts:`), and 3 for flags. Deterministic-only: judgment calls (is a scenario genuinely behaviour, a requirement genuinely testable) stay with the review subagents.
- `merge-config.test.cjs` — 37 cases: the round-trips and refusals above; a few tests use real subprocess timing/permissions and can't be simulated by reading the code. Same subprocess split as `vendor-skills.test.cjs`.
- `vendor-skills.test.cjs` — 11 cases over the pure helpers only (`sha256`, lock round-trip + malformed rejection, `walkFiles` + exclusions + missing-dir, `diffTrees` + `only`-restriction + vendored-side ignores, `verifyIntegrity`, `renderVendorMd`). The git-backed `run()` needs network — exercise by hand with `node scripts/vendor-skills.cjs --check`.
- `floor-guard.test.cjs` — 19 cases, each in a throwaway git repo: clean change; each Python and JS/TS suppression form; security suppression as its own rule with line text (and any secret) never printed; skips in existing tests (unittest, pytest, `skipTest`); the Odoo `'-standard'` vs `'-at_install'`/`'post_install'` distinction; new-file skip exemption; `cursor.skip(` vs `.skip(`; deleted test vs `git mv` vs plain `mv`; assertions moved / edited / dropped change-wide; stubs and swallowed exceptions; `--base`; untracked binaries skipped; exit-2 cases.
- `scripts/opengrep-rules.test.cjs` — every rule has a positive and a negative case; three engine tests (see §8) skipped when opengrep is absent.

Conventions for newly found gaps in these scripts: land the test asserting current behavior first with a `KNOWN GAP:` prefix, flip it to `FIXED:` when fixed (the TDD signal), and mark deliberate non-fixes `KNOWN LIMITATION:` in the code comment and its own test — never fix blind.

`scripts/package.json` exists only to give `merge-config.test.cjs` a resolvable `yaml` devDependency; `lint.cjs` and `floor-guard.cjs` have zero dependencies. `scripts/node_modules/` is gitignored; `package-lock.json` is committed for reproducible installs.
