# AGENTS.md

Guide for coding agents working in this repo.

See [README.md](README.md) for what this repo is and the file layout. Nothing here runs as an app — it's consumed by the OpenSpec CLI in downstream repos.

**This file is rules only.** The rationale, incidents, and measurements behind every rule live in [docs/DECISIONS.md](docs/DECISIONS.md) — read the linked section before proposing to change a rule, not instead of following it.

## Hard rules

- MUST NOT run `git commit` (or `git push`) unless the user explicitly asks for it in that turn. Finishing an edit, even a multi-file one the user clearly wants, is not by itself a request to commit — leave the working tree staged/unstaged and say what changed. A commit earlier in the session is not standing permission for later changes.
- Never hand-edit anything under `skills/vendor/` — `scripts/vendor-skills.cjs` (`--check` reports drift, `--apply` pulls upstream and rewrites `skills/vendor/vendor-lock.json`, `--source <owner/repo>` limits to one upstream repo) is the only sanctioned way to change those files.
- The installer has no flags, on purpose (see README) — don't add any unless asked. `install-schema.sh` (bash) and `install-schema.ps1` (PowerShell) are two copies kept in lockstep: same steps, same order, same messages, no flags on either. Any change to one must be mirrored in the other.
- Skills install via a single `npx skills add ${REPO}/skills --full-depth` call — `--full-depth` is required: the default discovery walk stops at `skills/hrt-*/` and silently skips everything under `skills/vendor/`, and the installer's "Installed skills" echo would not reveal the gap (why: DECISIONS §6). The installer copies only `schema.yaml` and `templates/*` from its clone — never `cp -r` the whole clone. A failed skill install stops the installer (same as a failed schema clone); skills aren't optional for a schema whose instructions point at them.
- Repo-wide MUSTs that apply to every phase belong in `./openspec/config.yaml`'s `context:` — written once by the installer via `scripts/merge-config.cjs`, not duplicated into each `instruction:` block (why: DECISIONS §12).

## Editing schema.yaml

Everything lives in `artifacts[]` (`id`, `generates`, `template`, `instruction`, `requires`) plus a top-level `apply` block. Each `instruction` is a prompt an agent runs at that phase — treat wording changes as prompt engineering, not prose cleanup. `requires` is the dependency graph that gates phase order — keep it accurate. If an instruction references a template section, update `templates/<id>.md` to match.

Per-phase invariants (why: [docs/DECISIONS.md](docs/DECISIONS.md) §1–§5):

- **proposal** is the only intent document — no `discovery` phase (removed in v15). Interview: `grilling`, capped at 4 questions per round and 4 rounds, the override written in the instruction (the vendored skill must not be hand-edited). Change-size rule: ≥2 independent, separately shippable slices → ask once "one change or several?" (default one change, never split without the answer, asked even in dark mode); deferred slices under `## Out of Scope`. No size threshold on purpose; no `openspec/BACKLOG.md`. No model review — `hrt-artifact-lint --phase=proposal` plus the user's read-and-confirm replace it. `## External Dependencies` is one row per out-of-codebase claim, each needing a primary source or a completed `research` run ("none" if fully internal); a "no" row blocks finalizing, and the lint checks it.
- **design.md is mandatory for every change** — no "create only if" gate. Depth varies (a pure config/data/infra change gets thin sections and a "no new code surface" `## Shape / Seams` line) but the file always exists: `align` treats absence as HIGH, and the seam-skip keys on section content, not file absence. `## Shape / Seams` carries test boundaries to `apply`; `align`'s `specs <-> design` dimension checks every scenario has one; a thin design (no code surface, ≤1 decision) gets `hrt-adversarial-authoring`'s Destructive Critic only, not the Structural Auditor.
- **tasks.md**: every group carries `Covers:` (exact scenario names, semicolon-separated, or `none` for a prefactor or expand/migrate/contract group) and `Depends on: none | 1, 2` (required since v19; a group with no line reads as depending on the group before it). Each design `[Threat T<n>: ...]` line has a unique id that a group also lists in `Covers:`; a covering group needs a task tagged `[security]`. `hrt-artifact-lint` checks scenario↔task and threat↔task coverage both directions by name and id, so `align` no longer judges them. There is deliberately no `Touches:` or `Test:` line — declared dependencies are the only isolation.
- **Reviews are digests, not per-item questions**: every HIGH DECISION, scope change, one-way door, or High-severity security trade-off is shown together with the others and answered one by one ("ok" never covers it); everything else is one digest "ok" accepts, at most 5 LOW findings shown. Consequence gate: a finding is actionable only if it names what a reader or implementer concretely hits when it's unfixed; "defer it / accept the drift" is not an alternative; never auto-resolve a finding with a clean fix in hand. `specs` and `design` reviewers don't re-open a premise `proposal.md` settled.
- **EGM rules** (all three review skills): a reviewer subagent that fails, times out, returns nothing, or cannot read an input is retried once, then recorded as `not run` — never a clean review, always blocking (artifact not finalized; `align` stops before WALKTHROUGH; `apply`'s 3rd pass `not run` = RELEASE BLOCKER). A host where no subagent can be spawned is the same case: the skill stops and reports, it does not ask whether to continue or review in the same context. A recommendation to reject a finding must name the file and line or section to check, or be labelled `unchecked reason:` in the digest.
- **align**: VERIFY runs only when ALIGN raised a HIGH; WALKTHROUGH is a digest led by specs, then design and seams, then the scenario → group → seam table, then the lint's `Size facts:` line. The `tasks graph` dimension checks `Depends on:` edges are true (an edge with no real need is LOW); align's lint pass covers `tasks.md` too, since align is the next phase.

Instructions are thin pointers to skills, not inlined prompt text (`proposal`→`grilling` + conditional→`research`, which fires when feasibility rests on an unverified external claim — a third-party API's actual capabilities, a library's documented limits, a standard's spec; `specs`/`design`→`hrt-adversarial-authoring` + `hrt-security-pass`; `tasks`/`align`/`apply`→`hrt-dark-mode-routing` one line each — the routing skill is the single source of truth for where a dark-mode finding goes (why: DECISIONS §11); `align`→`hrt-align-consistency-review`; `apply` P1→`tdd`, P2→`hrt-apply-code-review`, P3→`hrt-mr-brief`; `apply` P1/P2→`diagnosing-bugs` conditional; `hrt-artifact-lint` named by `proposal`, run inside the reviews elsewhere). Two standing exceptions to remember when editing: reference `grilling` directly, never `grill-me` (a dead-end pointer: `disable-model-invocation: true` — check any new upstream skill for this and for same-repo delegate targets before vendoring); and `plain-language-writing` is pointed to *from inside* other instructions and skills at the specific line producing user-facing text, never from a phase of its own (skills can't reference files across skill folders).

## Skills

- Local skills: `skills/<name>/SKILL.md` at repo root, so a future schema could reuse them; frontmatter is just `name` + `description`. Local ones take the `hrt-` prefix — the unprefixed exception is `plain-language-writing` (a plain rule-list descriptor); new local skills take the prefix. Vendored externals: `skills/vendor/<name>/`, each with the upstream `SKILL.md` (+ bundled files), the source `LICENSE`, and a generated `VENDOR.md`; `vendor-lock.json` pins source, path, commit, and per-file SHA-256. To vendor a new one: check for `disable-model-invocation`/same-repo delegates (see above), add the `vendor-lock.json` entry (`source`, `sourceType: "github"`, `sourceRef`, `sourceCommit`, `sourcePath`, `license`; `only: [...]` if the skill lives at the source repo root), run `node scripts/vendor-skills.cjs --apply`.
- **hrt-security-pass**: tiny SKILL.md (trust-boundary gate + pointer). If the gate fires, `references/method.md` holds the STRIDE questions, the surface→list-file table, the "leave out" rules, and the fixed per-threat line `[Threat: <category>, <High|Medium|Low>] → Mitigation (<Cheat Sheet name or CWE>)`, or `Security pass: skipped - <reason>`. `references/` = one ~1–2KB file per list (web, API, mobile, LLM, agentic, NHI Top 10; CICD-SEC-3 only; CWE Top 25; `business-flow.md`; `odoo.md`), read only for touched surfaces. **Format contract for those files**: quote official titles only — no pasted prose, no invented titles; keep a source URL and licence note per file; write the questions for this skill; `agentic-top10-2026.md` stays flagged (the official page doesn't list the titles); the CWE file keeps MITRE's copyright/licence sentence (a reuse condition); never add a framework file without checking it against that framework's own docs. New surface = one file in the same format + one row in `method.md`'s table. Its lint rule raises WARN (never ERROR) when proposal or specs name a trust-boundary keyword but `design.md` has neither a `[Threat` line nor the skip line; `align` judges whether the boundary is real. (Why this shape: DECISIONS §7.)
- **hrt-security-pass/opengrep/**: our own rules — `common.yml` (any-repo rules, Python + JS/TS) and `odoo.yml` (Odoo-only rules), each restating a `references/odoo.md` hint; the yml files are the source of truth for the lists. The review runs the whole folder on the files the change touches (tracked files differing from the base branch **plus** untracked ones; **never** `--baseline-commit`, which silently skips unstaged+untracked work — see DECISIONS §8). It is **required** whenever the diff touches a `.py`, `.js`, `.jsx`, `.ts` or `.tsx` file, or an `.xml` in a repo with a `__manifest__.py`; a docs-only change needs nothing. Required means no way round: command not found/disabled/erroring = automatic HIGH (MECHANICAL), the loop does not stop, an unresolved one ends as a RELEASE BLOCKER. The agent does not install it, look for another copy, offer a skip, or accept a waiver; dark mode does not route it to a decision gate. Results are candidates, never an automatic HIGH: keep a candidate only if the changed code is exploitable, dismiss only with a one-line reason. Rules are local files — no registry is contacted, no scanner binary is bundled. Only `opengrep` is named in the schema; a repo with its own scanner is already covered by step 1's repo commands. For any other language a clean run says nothing, and `hrt-mr-brief` says so.
- **hrt-apply-code-review**: step 1 runs `floor-guard.cjs` (same base branch as the scan). The guard only flags moves that turn a check green without fixing code — added suppression comments, added skips in a test file that existed before the change, deleted test files (renames excluded), a change-wide drop in assertion count, added stubs/swallowed exceptions in production code; see the script for the exact patterns. It is not a linter: exit 1 never blocks by itself, the reviewer classifies each flag in step 5, and an already-answered question is not re-asked on a later pass. Patterns cover Python (incl. unittest/Odoo) and JS/TS only — add an ecosystem after a real incident, not before. The performance lens (N+1, unbounded fetch, no pagination, hot-path allocation) is always LOW DECISION. `apply` P1 writes RED output into `retro-log.md` next to `tasks.md` — the change's single working log (RED output, per-group record, review tally, phase times); nothing lints `retro-log.md` or `mr-brief.md`; the `[security]` mutation probe stays deferred. (Calibration: DECISIONS §9.)
- **hrt-mr-brief** (apply P3) writes `mr-brief.md` (Summary / Evidence / Merge Danger) next to `tasks.md`, sourced from the change's own artifacts and test runs. Keep it schema-generic: headings in English, prose follows `proposal.md`'s language, no downstream team or tooling named, generic paste-safety only (no secrets or personal data, no closing keywords, no line starting with `/`). `apply` itself never commits, pushes, or touches the review system. (Origin: DECISIONS §10.)

## Templates

Markdown skeletons, not filled-in examples. Keep placeholders as HTML comments, e.g. `<!-- Task description -->`.

## Validating changes

No test suite for `schema.yaml`/`templates/` — check by hand: valid YAML, `requires` graph with no cycles or missing ids, every `template:` file actually present. If the schema is installed in an OpenSpec-managed repo, `openspec validate --strict` there is the real test of whether an instruction change broke anything downstream.

The scripts and bundled lints have test suites: `cd scripts && npm install && npm test` (`node --test merge-config.test.cjs lint.test.cjs vendor-skills.test.cjs floor-guard.test.cjs`). Coverage overview and bug history: [docs/DECISIONS.md](docs/DECISIONS.md) §13–§14.

- `lint.cjs` and `floor-guard.cjs` live in their skill folders because they ship downstream via `npx skills add`; their tests (`scripts/lint.test.cjs`, `scripts/floor-guard.test.cjs`) deliberately stay in `scripts/` so they do NOT ship — keep each pair in sync.
- `scripts/package.json` exists only to give `merge-config.test.cjs` a resolvable `yaml` devDependency; `lint.cjs` and `floor-guard.cjs` have zero dependencies. `scripts/node_modules/` is gitignored; `package-lock.json` is committed for reproducible installs.
- Run the matching suite after any change to a `.cjs`. Run `npm test` with opengrep installed on the machine before releasing a rule change — its engine tests skip when the binary is absent.
- Conventions for newly found gaps: land a test asserting current (undesirable) behavior prefixed `KNOWN GAP:` first, flip it to `FIXED:` as the TDD signal to fix, and mark deliberate non-fixes `KNOWN LIMITATION:` in the code comment and its own test. Never fix blind.
