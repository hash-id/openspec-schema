# AGENTS.md

Guide for coding agents working in this repo.

See [README.md](README.md) for what this repo is and the file layout. Nothing here runs as an app — it's consumed by the OpenSpec CLI in downstream repos.

## Editing schema.yaml

Everything lives in `artifacts[]` (`id`, `generates`, `template`, `instruction`, `requires`) plus a top-level `apply` block. Each `instruction` is a prompt an agent runs at that phase, so treat wording changes as prompt engineering, not prose cleanup.

`requires` is the dependency graph that gates phase order — keep it accurate. If an instruction references a template section, update `templates/<id>.md` to match.

The `proposal` instruction points at the `hrt-change-size-gate` skill from its **What Changes** bullet — if the draft bundles several independent slices, the agent asks the user whether to split rather than proceeding (default: one change, agent never splits on its own). The skill also records the split: `## Out of Scope` in `proposal.md`, a `discovery.md` Key Decisions entry, and `openspec/BACKLOG.md` (created at runtime, not provisioned by the installer; the OpenSpec CLI ignores bare `.md` files under `openspec/`). `discovery` reads `BACKLOG.md` as interview context if it exists (inline in the instruction, not via the skill). `design.md`'s `## Shape / Seams` section carries the test boundaries forward to `apply`; `align` has a `specs <-> seams` dimension checking every scenario has one, and `hrt-adversarial-authoring`'s `design` pass reviews them. See `docs/research/2026-08-27-mattpocock-skills-gate-and-seams.md`.

`design.md` is mandatory for every change — the `design` instruction has no "create only if" gate. Depth varies (a pure config/data/infra change gets thin sections and a "no new code surface" Shape / Seams line) but the file always exists, so `align` treats its absence as HIGH and the seam-skip keys on section content, not file absence. Removes the branch where an agent wrongly skipped design.md on a callable-code change and left `apply`'s seam override with nothing to read.

`proposal.md`'s `## External Dependencies` table is one row per out-of-codebase claim feasibility rests on, each needing a primary source or a completed `research` run ("none" if fully internal). Makes the `research`-skill trigger structural — a "no" row blocks finalizing — instead of an agent judgment call. `hrt-adversarial-authoring`'s Destructive Critic checks it.

Several instructions are thin pointers to skills instead of inlined prompt text — `discovery`→`grilling`, `proposal`→`hrt-change-size-gate` (from the What Changes bullet), `align`→`hrt-align-consistency-review`, `apply` Phase 1→`tdd`, `apply` Phase 2→`hrt-apply-code-review`, `proposal`/`specs`/`design`→`hrt-adversarial-authoring`, `hrt-artifact-lint` (the deterministic structure lint — bundled `lint.cjs`; no phase names it directly — `proposal`/`specs`/`design` run it inside `hrt-adversarial-authoring`, `align` runs it inside `hrt-align-consistency-review`, and align's pass covers `tasks.md` too since align is the next phase), `proposal`/`specs`/`design`/`tasks`/`align`/`apply`→`hrt-dark-mode-routing` (one line per phase — replaced the per-phase dark-mode carve-out paragraphs that used to be inlined), plus conditional pointers from `design`/`specs` to the security skills (`stride-analysis-patterns`, `threat-mitigation-mapping`, `security-requirement-extraction`), from `discovery`/`proposal` to `research` (mattpocock/skills) for when feasibility rests on an unverified external claim - a third-party API's actual capabilities, a library's documented limits, a standard's spec - as opposed to something answerable from this codebase, and from `apply` Phase 1 and Phase 2 (inside `hrt-apply-code-review`'s own resolution step) to `diagnosing-bugs`, for when a test keeps failing or a fix's root cause isn't obvious. `humanizer` is pointed to from inside `hrt-adversarial-authoring` (Author Notes, both reviewers' output), `hrt-align-consistency-review` (findings shown to the user), and `hrt-apply-code-review` (findings shown to the user) — these are agent-reasoning surfaces (author notes, review findings), not COMMS (live dialogue) or ARTIFACT (persistent spec prose) territory, so `plain-language-writing`'s two rule sets don't fit; `humanizer`'s job (strip AI-writing tells — em-dash chaining, hedging, filler) is a distinct concern from either. The local skills (`hrt-align-consistency-review`, `hrt-apply-code-review`, `hrt-adversarial-authoring`, `hrt-artifact-lint`, `plain-language-writing`, `hrt-change-size-gate`, `hrt-backlog-reconcile`, `hrt-dark-mode-opt-in`, `hrt-dark-mode-decision-gate`, `hrt-dark-mode-routing`) are this repo's own, at `skills/<name>/SKILL.md`, self-contained — `hrt-artifact-lint` bundles its own `lint.cjs` (zero deps, plain Node) in the skill folder — installed automatically by `npx skills add`, no installer copy step — and `hrt-dark-mode-routing` is the single source of truth for where a dark-mode finding goes (each phase points at it in one line rather than carrying its own carve-out); `hrt-change-size-gate` has some `tempa-spec` wiring (BACKLOG.md, discovery.md sections) but the sizing judgment itself is schema-agnostic, same coupling level as `hrt-adversarial-authoring`. The rest are external (`mattpocock/skills`, `wshobson/agents`, `blader/humanizer`), provisioned by the installer — see `docs/research/2026-07-16-skills-as-dependencies-plan.md` for why each was inlined, split, or referenced externally.

`plain-language-writing` isn't pointed to by its own artifact instruction — it's pointed to *from inside* other instructions and skills, at whichever specific line produces user-facing text (a confirmation prompt, a blocker message) or artifact prose (a discovery.md/proposal.md/etc. section), because those points are scattered across `schema.yaml`, `hrt-align-consistency-review`, and `hrt-adversarial-authoring` rather than owned by one phase. See `docs/research/2026-08-07-plain-language-non-native-readers.md` for the evidence behind its two rule sets (COMMS vs. ARTIFACT) and why they're split. Skills cannot reliably reference files inside another skill's folder once installed (no cross-skill path guarantee) — that's why this is a full skill of its own rather than a shared reference file, even though its content is just a rule list, not a process.

`discovery` points at `grilling` directly, not at `grill-me` — `grill-me` in `mattpocock/skills` is a dead-end pointer (`disable-model-invocation: true`, its `SKILL.md` just says "run a `/grilling` session"), so an agent can never self-invoke it. Reference `grilling` directly for any schema instruction that needs this interview. If a future `npx skills add` call references any other skill, check its `SKILL.md` for `disable-model-invocation` or a same-repo target it delegates to before assuming the name alone works from an instruction.

## Skills

Local skills live at `skills/<name>/SKILL.md` (repo root, not under `openspec/schemas/tempa-spec/`) so any future schema added to this repo could reuse them — today `tempa-spec` is the only schema here. Frontmatter is just `name` + `description` (the format `vercel-labs/skills` and Claude Code both expect) — no repo-specific extensions.

Local skills are prefixed `hrt-` to namespace them against the external ones (`mattpocock/skills`, `wshobson/agents`, `blader/humanizer`). The lone exception is `plain-language-writing`, kept unprefixed because its name is a plain descriptor of a rule list, not an `hrt-` process — new local skills should take the prefix.

`hrt-backlog-reconcile` is the one local skill no `schema.yaml` instruction points at — user-invoked only (`/hrt-backlog-reconcile`), a hand-run pass that reconciles `openspec/BACKLOG.md` against `openspec/specs/` and proposes deleting covered entries. Outside the pipeline because its natural trigger, `openspec archive`, is human-run with no hook point; best run right after archiving. Shares `BACKLOG.md`'s entry format with `hrt-change-size-gate`, duplicated in both SKILL.md files (no cross-skill path guarantee).

## Templates

Markdown skeletons, not filled-in examples. Keep placeholders as HTML comments, e.g. `<!-- Task description -->`.

## Installer

No flags, on purpose (see README). Don't add any unless asked.

It clones `master` into a temp dir, copies only `schema.yaml` and `templates/*`, then provisions skills via `npx skills add` (external: `mattpocock/skills` (`grilling`, `tdd`, `diagnosing-bugs`, `research`), `wshobson/agents`, `blader/humanizer`; local: this repo's own `skills/`), then writes `./openspec/config.yaml`'s `schema:` and `context:` fields via `scripts/merge-config.cjs` (a Node script run against a throwaway `npm install --no-save yaml` in the temp dir — real YAML parse/modify/write, not line-based text editing, so an existing `context:` that's multiline, block-scalar, or a commented-out sample survives instead of being clobbered). It never `cp -r`s the whole clone for the schema.yaml/templates step — keep it that way; the `npx skills add` calls do their own independent clone and aren't part of that invariant. A failed skill install stops the installer (same as a failed schema clone) — skills aren't optional for a schema whose instructions point at them. Test it in a scratch dir, since it writes to `./openspec/` (and `.agents/skills/`) relative to wherever it's run.

`context:` is OpenSpec's CLI-injected-into-every-phase mechanism (confirmed against `Fission-AI/OpenSpec` issue #1524's description of current behavior — project-level `context` in `config.yaml` is "reliably applied" by the CLI to all artifact instruction generation, unlike agent-read files like this one). Repo-wide MUSTs that apply to every phase (e.g. codebase exploration: MUST use codegraph and ripgrep together, codebase-memory-mcp and built-in grep/glob only as fallback when both are unavailable) belong there, written once by the installer, rather than duplicated into each `instruction:` block in `schema.yaml` — YAML anchors/aliases can't substitute mid-paragraph inside a block-scalar `instruction: |` string (verified: an alias placed inside `|` text stays literal, it only expands as a whole-node value), so per-instruction duplication was the only in-file alternative and `context:` avoids it entirely. There is no CLI subcommand for writing `context:` (checked `openspec config` — it only touches the global `~/.config/openspec/config.json`, not the project `config.yaml`), hence the hand-rolled merge script.

Two copies, kept in lockstep: `install-schema.sh` (bash) and `install-schema.ps1` (PowerShell). Same steps, same order, same messages, no flags on either. Any change to one — new skill, new step, new error message — must be mirrored in the other.

## Git commits

MUST NOT run `git commit` (or `git push`) unless the user explicitly asks for it in that turn. Finishing an edit, even a multi-file one the user clearly wants, is not by itself a request to commit — leave the working tree staged/unstaged and say what changed; wait for the user to say "commit" (or equivalent) before running it. A commit earlier in the session does not carry forward as standing permission for later changes.

## Validating changes

No test suite for `schema.yaml`/`templates/` — check by hand: valid YAML, `requires` graph with no cycles or missing ids, every `template:` file actually present. If the schema is installed in an OpenSpec-managed repo, `openspec validate --strict` there is the real test of whether an instruction change broke anything downstream.

`scripts/merge-config.cjs` (the installer's config.yaml merger) and `skills/hrt-artifact-lint/lint.cjs` (the deterministic artifact structure lint) BOTH have test suites, run together by `cd scripts && npm install && npm test` (`node --test merge-config.test.cjs lint.test.cjs`). `lint.cjs` lives in its skill folder because it ships downstream via `npx skills add`; its test, `scripts/lint.test.cjs`, deliberately stays in `scripts/` so it does NOT ship — keep the two in sync. `scripts/package.json` exists only to give `merge-config.test.cjs` a resolvable `yaml` devDependency — `lint.cjs` has zero dependencies. `scripts/node_modules/` is gitignored; `package-lock.json` is committed for reproducible test installs.

`lint.test.cjs` covers 23 cases via `node:test` (hashtag counts, scenario-as-bullet, requirement with no scenario, missing WHEN/THEN, SHALL/MUST as WARN, unknown delta header, REMOVED without Reason/Migration, capability↔spec-file both directions, non-kebab capability, missing/absent design.md section, `Covers:` target not in specs, "no new code surface" skip, archive task, non-checkbox bullet as WARN, unverified/verified External Dependencies rows, missing proposal.md section, bad-args exit 2, template-placeholder capability ignored). Run it after any change to `lint.cjs`. The lint is deterministic-only — the judgement calls (is a scenario genuinely behaviour, is a requirement genuinely testable) stay with the review subagents.

`merge-config.test.cjs` covers 37 cases via `node:test` (`npm test` — run it after any change to `merge-config.cjs`; a few tests use real subprocess timing/permissions and can't be simulated by reading the code). Core round-trip and refusal behavior: absent config file, config with `schema:` only (no `context:` key), existing `context:` as single-line quoted/unquoted scalar, multiline block-literal (`|`), multiline folded (`>`), null-ish forms (`context:` empty, `null`, `~`), a fully commented-out sample block, idempotent re-run, general re-parseability, a UTF-8 BOM, YAML 1.1-ambiguous barewords (`yes`/`no`/`on`/`off`) treated as strings not booleans, a merge-key-supplied `context:` (`<<: *anchor`) treated as absent since `doc.get` doesn't resolve merge keys, very long `contextText`, and markers containing regex metacharacters. Refused cleanly (non-zero exit, file untouched, no raw stack trace): `context:` as a non-string YAML node (list, mapping, or `*alias`), malformed YAML (duplicate keys, tab indentation, a multi-document `---` stream) caught via `doc.errors` right after parsing, a symlinked `configPath` (dangling or not — checked via `lstatSync` before anything else touches the path), and filesystem errors (`EISDIR`, `EACCES`, etc. — mapped to a one-line message instead of Node's default uncaught-exception dump).

Three subagents (one per angle — YAML data-shape, filesystem/OS, CLI-argument/adversarial) were run against this script to find edge cases beyond what manual review caught. Their findings became most of the tests above, plus four real bugs, all now fixed (tests prefixed `FIXED:` rather than the `KNOWN GAP:` prefix they carried while still open — keep using that convention for any newly found gap: land the test asserting current, undesirable behavior first, then flip it to desired behavior as the TDD signal to fix the script, rather than fixing blind):
- **Marker-version-drift** (real, already happened once in this repo's history per the `context:` wording change): the old `.includes(marker)` idempotency check couldn't tell "already merged" from "not yet merged," so a reworded `CONTEXT_MARKER`/`CONTEXT_TEXT` in a future installer would append a second, possibly-contradictory block forever instead of replacing the old one. Fixed by `replaceOrAppendBlock()`: an exact, line-anchored match of the marker line is searched for; if found, everything from that line through the next blank line (or end of string) is replaced wholesale; if not found, a new block is appended. This also fixed the two bugs below as a side effect, since line-anchored matching replaced substring matching.
- **Marker-as-substring false-positive idempotency**: a marker (or an accidentally near-empty one, e.g. a single space) that happened to already appear inside unrelated existing prose used to make the script treat the file as "already merged" and skip the real append, silently. Fixed by the same line-anchored match above — a marker only matches a line that equals it exactly, not any line containing it as a substring.
- **Symlinked `configPath` was followed and written through**, with no `lstat`/no-follow guard. Fixed: `fs.lstatSync` (not `fs.existsSync`, which follows symlinks and would report `false` for a dangling one, hiding it) runs before anything else touches the path; a symlink of any kind — dangling or not — is refused with a clean error.
- **Filesystem errors surfaced as raw Node stack traces**, not the script's own clean `console.error` style used for YAML-parse and non-string-context errors. Fixed: `readFileSync`/`mkdirSync`/`writeFileSync` are wrapped in try/catch, and `failWithCleanFsError()` maps common codes (`EISDIR`, `EACCES`, `EPERM`, `ENOSPC`, `ENOTDIR`) to a one-line message. Not fixed (documented, not tested — timing-dependent and not worth the complexity for a script whose caller already treats any non-zero exit as fatal): `writeFileSync` still truncates in place rather than write-temp-then-rename, so a kill mid-write could in principle leave `config.yaml` empty or partially written.

One limitation was found *during* the marker-drift fix itself and deliberately left as-is rather than fixed further, per `KNOWN LIMITATION:` in both the code comment above `replaceOrAppendBlock()` and its own test: block-end is inferred from the first blank line after the marker, so a `contextText` with an internal blank line (a multi-paragraph body) only gets its first paragraph replaced on a reword — later paragraphs from the old block survive as orphaned trailing text. Not a real risk today since the installer's `CONTEXT_TEXT` is always a single line; a real fix needs an explicit block-closing delimiter, which would change the format of every already-installed `config.yaml` to solve a problem that doesn't exist yet.
