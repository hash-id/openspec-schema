# AGENTS.md

Guide for coding agents working in this repo.

See [README.md](README.md) for what this repo is and the file layout. Nothing here runs as an app — it's consumed by the OpenSpec CLI in downstream repos.

## Editing schema.yaml

Everything lives in `artifacts[]` (`id`, `generates`, `template`, `instruction`, `requires`) plus a top-level `apply` block. Each `instruction` is a prompt an agent runs at that phase, so treat wording changes as prompt engineering, not prose cleanup.

`requires` is the dependency graph that gates phase order — keep it accurate. If an instruction references a template section, update `templates/<id>.md` to match.

`proposal` is the only intent document: there is no `discovery` phase or file (removed in v15; see `docs/research/2026-10-21-tempa-spec-weight-and-phase-reduction.md`). The phase opens with a `grilling` interview capped at 4 questions per round and 4 rounds (an override written in the instruction, since the vendored skill must not be hand-edited), then drafts. Its change-size rule is a short paragraph in the instruction, not a skill: if the interview shows two or more independent, separately shippable slices, ask once "one change or several?" (default one change, never split without the answer, asked even in dark mode) and list deferred slices under `## Out of Scope`. There is no size threshold on purpose (a large change whose parts depend on each other is one change), and no `openspec/BACKLOG.md`. The proposal has no model review: `hrt-artifact-lint --phase=proposal` (structure, plus WARN-only size and shape rules) and the user's read-and-confirm replace it, because with `discovery.md` gone nothing written exists for a reviewer to check it against. `design.md`'s `## Shape / Seams` section carries the test boundaries forward to `apply`; `align`'s `specs <-> design` dimension also checks every scenario has one, and `hrt-adversarial-authoring`'s `design` pass reviews them against `to-spec`'s rule (highest available entry point, fewest seams, ideal one). See `docs/research/2026-08-27-mattpocock-skills-gate-and-seams.md`.

`tasks.md` carries a `Covers:` line on every group (exact scenario names separated by semicolons, or `Covers: none` for a prefactor or expand/migrate/contract group), and each design `[Threat T<n>: ...]` line has a unique id that a group also lists in `Covers:` (for example `Covers: Successful export; T1`), and that group needs a task tagged `[security]`. `hrt-artifact-lint` checks both directions by name and id, so scenario-to-task and threat-to-task coverage are deterministic and `align` no longer judges them.

Review prompts are digests, not per-item questions (`hrt-adversarial-authoring` step 4, `hrt-align-consistency-review` step 8, `hrt-apply-code-review` step 8). A finding that needs its own answer — every HIGH DECISION, a change to settled scope, a one-way door, a High-severity security trade-off — is shown together with the others in one message and answered one by one; "ok" never covers it. Everything else is one digest that "ok" accepts, with at most 5 LOW findings shown. `align`'s VERIFY runs only when ALIGN raised a HIGH (measured: skips 3 of 8 productive runs, accepted), and its WALKTHROUGH is a digest led by specs, then design and seams, then the scenario → group → seam table, then the lint's `Size facts:` line.

`design.md` is mandatory for every change — the `design` instruction has no "create only if" gate. Depth varies (a pure config/data/infra change gets thin sections and a "no new code surface" Shape / Seams line) but the file always exists, so `align` treats its absence as HIGH and the seam-skip keys on section content, not file absence. The adversarial review scales with it: a thin design.md (no code surface, ≤1 decision) gets `hrt-adversarial-authoring`'s Destructive Critic only, not the Structural Auditor. Removes the branch where an agent wrongly skipped design.md on a callable-code change and left `apply`'s seam override with nothing to read.

Both review skills apply a **consequence gate**: a finding is only actionable (`hrt-adversarial-authoring`'s `## Required Changes`, `hrt-align-consistency-review`'s HIGH/MEDIUM) if it names what a reader or implementer concretely hits when it's unfixed. Critique that names no such consequence ("the premise is thin") drops to a non-blocking batch — `## Suggested Improvements` in adversarial, LOW DECISION findings shown once in align — never a per-item question. Both also treat "defer it / accept the drift" as a non-alternative, and neither auto-resolves a finding with a clean fix in hand when a competent author could pick differently. `hrt-adversarial-authoring`'s `specs` and `design` reviewers don't re-open a premise `proposal.md` settled. See `docs/research/2026-09-09-technical-writing-adversarial-drafting-skills.md`.

`proposal.md`'s `## External Dependencies` table is one row per out-of-codebase claim feasibility rests on, each needing a primary source or a completed `research` run ("none" if fully internal). Makes the `research`-skill trigger structural — a "no" row blocks finalizing — instead of an agent judgment call. `hrt-artifact-lint` checks it.

Several instructions are thin pointers to skills instead of inlined prompt text — `proposal`→`grilling` (the capped interview), `align`→`hrt-align-consistency-review`, `apply` Phase 1→`tdd`, `apply` Phase 2→`hrt-apply-code-review`, `apply` Phase 3→`hrt-mr-brief`, `specs`/`design`→`hrt-adversarial-authoring`, `hrt-artifact-lint` (the deterministic structure lint — bundled `lint.cjs`; `proposal` names it directly, `specs`/`design` run it inside `hrt-adversarial-authoring`, `align` runs it inside `hrt-align-consistency-review`, and align's pass covers `tasks.md` too since align is the next phase), `specs`/`design`/`tasks`/`align`/`apply`→`hrt-dark-mode-routing` (one line per phase — replaced the per-phase dark-mode carve-out paragraphs that used to be inlined), a pointer from `design`/`specs` to `hrt-security-pass` (the plan-time security pass, see below), plus conditional pointers from `proposal` to `research` (mattpocock/skills) for when feasibility rests on an unverified external claim - a third-party API's actual capabilities, a library's documented limits, a standard's spec - as opposed to something answerable from this codebase, and from `apply` Phase 1 and Phase 2 (inside `hrt-apply-code-review`'s own resolution step) to `diagnosing-bugs`, for when a test keeps failing or a fix's root cause isn't obvious. `humanizer` was dropped in v15 (pointers removed, vendored copy deleted): it had no evidence behind it and cost 30 KB. The local skills (`hrt-align-consistency-review`, `hrt-apply-code-review`, `hrt-adversarial-authoring`, `hrt-artifact-lint`, `hrt-security-pass`, `plain-language-writing`, `hrt-mr-brief`, `hrt-dark-mode-opt-in`, `hrt-dark-mode-decision-gate`, `hrt-dark-mode-routing`) are this repo's own, at `skills/<name>/SKILL.md`, self-contained — `hrt-artifact-lint` bundles its own `lint.cjs` (zero deps, plain Node) in the skill folder — installed automatically by `npx skills add`, no installer copy step — and `hrt-dark-mode-routing` is the single source of truth for where a dark-mode finding goes (each phase points at it in one line rather than carrying its own carve-out). The rest originate upstream (`mattpocock/skills` — `grilling`, `tdd`, `diagnosing-bugs`, `research`) but are **vendored into `skills/vendor/<name>/`**, not fetched from their own repos at install time. The installer provisions them in the same single `npx skills add ${REPO}/skills --full-depth` call that installs the `hrt-*` skills (`--full-depth` is required — the default walk stops at `skills/hrt-*/` and skips `skills/vendor/*`). Each vendored folder keeps the source repo's `LICENSE` (the one remaining upstream, `mattpocock/skills`, is MIT) and a generated `VENDOR.md` recording the source path and pinned commit. `scripts/vendor-skills.cjs` (`--check` reports drift, `--apply` pulls upstream and rewrites `skills/vendor/vendor-lock.json`, `--source <owner/repo>` limits either to one upstream repo) is the only sanctioned way to change anything under `skills/vendor/` — never hand-edit those files. See `docs/research/2026-07-16-skills-as-dependencies-plan.md` for why each was inlined, split, or referenced externally; the switch from install-time `npx skills add` per source repo to vendored copies was to cut 4 network clones to 1 and stop a third-party repo rename/outage from breaking installs.

`plain-language-writing` isn't pointed to by its own artifact instruction — it's pointed to *from inside* other instructions and skills, at whichever specific line produces user-facing text (a confirmation prompt, a blocker message) or artifact prose (a proposal.md/design.md/etc. section), because those points are scattered across `schema.yaml`, `hrt-align-consistency-review`, and `hrt-adversarial-authoring` rather than owned by one phase. See `docs/research/2026-08-07-plain-language-non-native-readers.md` for the evidence behind its two rule sets (COMMS vs. ARTIFACT) and why they're split. Skills cannot reliably reference files inside another skill's folder once installed (no cross-skill path guarantee) — that's why this is a full skill of its own rather than a shared reference file, even though its content is just a rule list, not a process.

`proposal` points at `grilling` directly, not at `grill-me` — `grill-me` in `mattpocock/skills` is a dead-end pointer (`disable-model-invocation: true`, its `SKILL.md` just says "run a `/grilling` session"), so an agent can never self-invoke it. Reference `grilling` directly for any schema instruction that needs this interview. Before vendoring any new external skill, check its `SKILL.md` for `disable-model-invocation` or a same-repo target it delegates to before assuming the name alone works from an instruction. To vendor a new one: add an entry to `skills/vendor/vendor-lock.json` (`source`, `sourceType: "github"`, `sourceRef`, `sourceCommit`, `sourcePath`, `license`; `only: [...]` if the skill lives at the source repo root), then run `node scripts/vendor-skills.cjs --apply`.

## Skills

Local skills live at `skills/<name>/SKILL.md` (repo root, not under `openspec/schemas/tempa-spec/`) so any future schema added to this repo could reuse them — today `tempa-spec` is the only schema here. Frontmatter is just `name` + `description` (the format `vercel-labs/skills` and Claude Code both expect) — no repo-specific extensions.

Vendored external skills live one level deeper, at `skills/vendor/<name>/`, each with the upstream `SKILL.md` (plus any bundled files — `tdd/tests.md`, `diagnosing-bugs/scripts/hitl-loop.template.sh`, etc.), the source repo's `LICENSE`, and a generated `VENDOR.md`. The installer's `npx skills add ${REPO}/skills` call passes **`--full-depth`** — without it the discovery walk stops one level down (`skills/hrt-*/` only) and silently skips everything under `skills/vendor/`, and the installer's "Installed skills" echo is a fixed string that wouldn't reveal the gap. Verified end-to-end against a local clone: with `--full-depth` all of them (19 skills when measured, 14 now) land flat in `.agents/skills/<name>/`, bundled files included. `skills/vendor/vendor-lock.json` pins each one's source repo, path, commit, and per-file SHA-256; `scripts/vendor-skills.cjs` is the refresh tool (see **Validating changes** and the skills paragraph in the intro).

Local skills are prefixed `hrt-` to namespace them against the vendored external ones (`grilling`, `tdd`, `diagnosing-bugs`, `research` — under `skills/vendor/`). The lone exception is `plain-language-writing`, kept unprefixed because its name is a plain descriptor of a rule list, not an `hrt-` process — new local skills should take the prefix. Vendored skills keep their upstream names unchanged.

Parallel apply is declared in `tasks.md`, not decided at apply time: a group may carry one `Depends on:` line (the `tasks` instruction explains them; `hrt-artifact-lint` checks structure, `hrt-align-consistency-review`'s `tasks graph` dimension checks that the graph is true). `apply` Phase 1 only schedules what is declared, and asks the user once to choose parallel or in order (no question in dark mode: in order). A group with no `Depends on:` depends on the group before it, so existing `tasks.md` files behave as before, and parallelism needs at least one group that is declared to start early. There is deliberately no `Touches:` or `Test:` line, to keep `tasks.md` short: the declared dependencies are the only isolation, `align`'s `tasks graph` dimension checks they are true, and `apply` watches for the failure that a missing edge causes (two concurrent groups changing the same file, or a test failing in code the group did not change). The concurrency limit is `min(floor(cores / 3), floor(available GB / 2))`, run in order when that is below 2 or cannot be read. Scheduling is a rolling frontier (as in mattpocock's `implement-spec`: a finished group immediately frees newly unblocked ones), not fixed waves. One shared working tree, no worktrees, only the orchestrator ticks checkboxes, and the full suite runs only at quiet points when no group is running. A group is the unit that `implement-spec` calls a ticket. Prefactoring (from `to-tickets`) is a `tasks` exception alongside wide-refactor: the `design` Decision records it, `tasks` makes it an early group. The limit formula lives only in the `apply` instruction.

`hrt-mr-brief` is `apply` Phase 3: it writes `mr-brief.md` (Summary / Evidence / Merge Danger) next to `tasks.md` for the reviewer. Adapted from `mattpocock/skills`' `pr` (itself credited to Dex Horthy's `show-me`) but local rather than vendored: the output is a file, not a PR body, and every section is sourced from the change's own artifacts and test runs. Apply Phase 1 keeps each task's RED output so Evidence can quote it. Keep it schema-generic: headings stay in English, prose follows `proposal.md`'s language, and it names no downstream team or tooling. It carries only generic paste-safety rules (no secrets or personal data, no closing keywords, no line starting with `/`). `apply` itself still never commits, pushes, or touches the review system.

`hrt-security-pass` is the `specs`/`design` security pass and the source of `apply`'s code-level security lens. `SKILL.md` is deliberately tiny (about 1.3 KB): only the trust-boundary gate and a pointer, so a change that touches no boundary pays almost nothing. If the gate fires, `references/method.md` holds the STRIDE questions per boundary crossing, a surface table that picks which list file to read, the "leave out" rules, and one fixed line per threat, `[Threat: <category>, <High|Medium|Low>] → Mitigation (<Cheat Sheet name or CWE>)`, or `Security pass: skipped - <reason>`. It replaced three vendored `wshobson/agents` skills (about 8 KB of `SKILL.md` plus 64 KB of Python-dataclass references that added no knowledge a model lacks). OWASP ASVS was evaluated and deliberately not adopted: it is web-application-centred, has no L1 requirements in V16 (logging and error handling), is CC BY-SA 4.0, and a lookup script plus attribution is more machinery than a plan-time check needs. `references/` holds one file per list (OWASP Top 10:2025 web, API Security Top 10:2023, Mobile Top 10 2024, LLM Top 10 2025, Agentic Top 10 2026, NHI Top 10 2025, the CI/CD Security Risks entry CICD-SEC-3 only (`cicd-top10.md`, read when a third-party package is added or upgraded; the page has no version label, so the file name carries no year), MITRE CWE Top 25 2025, `business-flow.md` (the OWASP Web Security Testing Guide v4.2 section 4.10 titles, quoted; the page is "all rights reserved", so only titles are quoted and the questions are ours; it covers the abuse of money, stock, limit, and state flows that the Top 10 lists name in one line), and `odoo.md` framework hints for Odoo 18 and later, each point tagged with its Odoo documentation or source-docstring origin), each about 1 to 2 KB, read only for the surfaces a change touches. Each file quotes the official titles, keeps a source URL and licence note, and carries questions written for this skill. Keep the files that way: no pasted prose from OWASP or MITRE, no invented titles, and `agentic-top10-2026.md` stays flagged because the official page does not list the titles. The CWE file must keep MITRE's copyright and licence sentence (a condition of reuse). To add a surface, add one file in the same format and one row in the skill's table. Do not add a framework file without checking it against that framework's own documentation. `lint.cjs` raises a WARN (never an ERROR) when proposal or specs name a trust-boundary keyword but `design.md` has neither a `[Threat` line nor the skip line; `align` judges whether the boundary is real. Code-level security runs in `apply` Phase 2 (`hrt-apply-code-review`): it runs whatever security commands the downstream repo already configures, scoped to the diff, and bundles no scanner binary (stack-specific, rules licences differ, scanner supply chains have been attacked). It does bundle our own rules and require the developer to install `opengrep` (next paragraph), which is why the README says so. The review's security lens also asks for the source, the place that acts on it, and the missing defence, treats a defence as real only after its body is read, and keeps an unprovable finding as LOW DECISION instead of dropping it. Evidence and sources: `docs/research/2026-10-15-security-approach-vendored-skills-vs-standards.md`.

`hrt-apply-code-review` bundles `floor-guard.cjs` (zero deps, plain Node, run in step 1 with the same base branch as the security scan). It flags the moves an agent makes to turn a check green without fixing the code: an added suppression comment (`# noqa`, `@ts-ignore`, `eslint-disable`, ...; `# nosec`, `nosemgrep`, `gitleaks:allow` as a separate security rule whose line text is never printed), an added skip in a test file that existed before the change (an added `'-standard'` Odoo tag counts; `'-at_install'`/`'post_install'` do not), a deleted test file (renames and a plain `mv` of identical content excluded), a drop in the assertion count across all test files (not per file), and an added stub or swallowed exception in production code. Patterns cover Python (including unittest and Odoo) and JS/TS only; add an ecosystem after a real incident, not before. It only flags: the reviewer classifies each flag in step 5, it is not a linter (exit 1 never blocks the loop by itself), and an answer the user already gave is not asked again on a later pass. Adapted from `addyosmani/agent-skills`' floor guard (MIT, credited in the script header). The per-change counting and the new-file skip exemption come from a measurement on three downstream repositories, where 18 of 18 per-file assertion drops were moves, rewrites, or spec changes, and the one real weakening was blanket `@ts-ignore` in tests. The same skill's performance lens (N+1, unbounded fetch, no pagination, hot-path allocation) is always LOW DECISION. `apply` Phase 1 writes RED output to `red-log.md` next to `tasks.md` so Phase 2 and `hrt-mr-brief` read it from disk. A mutation probe for `[security]` tests was designed and deferred until a weak security test is seen in practice. Evidence and decisions: `docs/research/2026-10-25-addyosmani-agent-skills-evaluation.md`.

`hrt-security-pass/opengrep/` holds our own rules for `opengrep`, in two files. `common.yml` has eleven rules for any repo, Python and JavaScript/TypeScript only (a shell command that is not a fixed string, pickle/marshal/`yaml.load` without a safe loader, `eval`/`exec`/`new Function` on built code, a query built as a string, certificate checking turned off, `tempfile.mktemp`, an HTML sink written from a variable). `odoo.yml` has five that match only Odoo constructs (public route with `sudo()`, `csrf=False`, `safe_eval`, `Markup` built with an f-string, `t-raw` in QWeb), each restating a hint in `references/odoo.md`. `hrt-apply-code-review` step 1 runs the whole folder on the files the change touches (tracked files that differ from the base branch, plus untracked ones; not `--baseline-commit`, which on opengrep 1.11.1 and 1.32.0 silently skips unstaged edits and untracked files, and the review runs before anything is committed) in any repo, and it is **required** whenever the diff touches a `.py`, `.js`, `.jsx`, `.ts` or `.tsx` file, or an `.xml` file in a repo with a `__manifest__.py` (a docs-only change needs nothing). For any other language a clean run says nothing, and `hrt-mr-brief` says so. Add a language after a real need, not before (same rule as the floor guard). Required means no way round it, by the maintainer's decision: if the command is not found, is disabled, or exits with an error, that is an automatic HIGH (MECHANICAL, fix outside the code), the loop does not stop, and an unresolved one ends as a RELEASE BLOCKER. The agent does not install it, does not look for another copy, does not offer a skip, and accepts no waiver; dark mode does not route it to a decision gate. The developer installs opengrep (the README has the commands); the installer does not, and has no flag for it. The reason it is required: on `sip` the scan found about twenty SQL interpolations that the Semgrep registry packs did not (see the research doc). Its results stay candidates, never an automatic HIGH, because the rules have not been measured on enough real code; a candidate is kept only if the changed code is exploitable and dismissed only with a one-line reason. The rules are local files, so no registry is contacted, and they are our own. Only `opengrep` is named in the schema; a repo that configures another scanner is already covered by the repo's own commands in step 1. Fixtures live in `scripts/fixtures/opengrep-rules/`, and `scripts/opengrep-rules.test.cjs` checks that every rule has a positive and a negative case; its three engine tests (`opengrep test`; scanning the changed files of a dirty repo finds committed, unstaged, staged and untracked work; and a KNOWN GAP test that pins the `--baseline-commit` behaviour above, so a fixed opengrep makes it fail and prompts a second look) are skipped when opengrep is not installed, so run `npm test` with opengrep on the machine before releasing a rule change. The rule tests passed on opengrep 1.11.1 and 1.32.0. Evidence: `docs/research/2026-10-25-sast-and-security-skills-landscape-evaluation.md` §4.2.

Markdown skeletons, not filled-in examples. Keep placeholders as HTML comments, e.g. `<!-- Task description -->`.

## Installer

No flags, on purpose (see README). Don't add any unless asked.

It clones `master` into a temp dir, copies only `schema.yaml` and `templates/*`, then provisions skills via a single `npx skills add ${REPO}/skills --full-depth` call (this repo's own `skills/` — both `hrt-*` and the vendored external skills under `skills/vendor/`; `--full-depth` is what makes the walk reach the nested `skills/vendor/` folder), then writes `./openspec/config.yaml`'s `schema:` and `context:` fields via `scripts/merge-config.cjs` (a Node script run against a throwaway `npm install --no-save yaml` in the temp dir — real YAML parse/modify/write, not line-based text editing, so an existing `context:` that's multiline, block-scalar, or a commented-out sample survives instead of being clobbered). It never `cp -r`s the whole clone for the schema.yaml/templates step — keep it that way; the `npx skills add` call does its own independent clone and isn't part of that invariant. A failed skill install stops the installer (same as a failed schema clone) — skills aren't optional for a schema whose instructions point at them. (Before this was one call, the installer made four — one per external source repo — which meant four network clones and a hard dependency on three third-party repos staying reachable (`mattpocock/skills`, `wshobson/agents`, `blader/humanizer`; the `wshobson/agents` skills have since been replaced by `hrt-security-pass`); vendoring collapsed that.) Test it in a scratch dir, since it writes to `./openspec/` (and `.agents/skills/`) relative to wherever it's run.

`context:` is OpenSpec's CLI-injected-into-every-phase mechanism (confirmed against `Fission-AI/OpenSpec` issue #1524's description of current behavior — project-level `context` in `config.yaml` is "reliably applied" by the CLI to all artifact instruction generation, unlike agent-read files like this one). Repo-wide MUSTs that apply to every phase (e.g. codebase exploration: MUST use codegraph and ripgrep together, codebase-memory-mcp and built-in grep/glob only as fallback when both are unavailable) belong there, written once by the installer, rather than duplicated into each `instruction:` block in `schema.yaml` — YAML anchors/aliases can't substitute mid-paragraph inside a block-scalar `instruction: |` string (verified: an alias placed inside `|` text stays literal, it only expands as a whole-node value), so per-instruction duplication was the only in-file alternative and `context:` avoids it entirely. There is no CLI subcommand for writing `context:` (checked `openspec config` — it only touches the global `~/.config/openspec/config.json`, not the project `config.yaml`), hence the hand-rolled merge script.

Two copies, kept in lockstep: `install-schema.sh` (bash) and `install-schema.ps1` (PowerShell). Same steps, same order, same messages, no flags on either. Any change to one — new skill, new step, new error message — must be mirrored in the other.

## Git commits

MUST NOT run `git commit` (or `git push`) unless the user explicitly asks for it in that turn. Finishing an edit, even a multi-file one the user clearly wants, is not by itself a request to commit — leave the working tree staged/unstaged and say what changed; wait for the user to say "commit" (or equivalent) before running it. A commit earlier in the session does not carry forward as standing permission for later changes.

## Validating changes

No test suite for `schema.yaml`/`templates/` — check by hand: valid YAML, `requires` graph with no cycles or missing ids, every `template:` file actually present. If the schema is installed in an OpenSpec-managed repo, `openspec validate --strict` there is the real test of whether an instruction change broke anything downstream.

`scripts/merge-config.cjs` (the installer's config.yaml merger), `skills/hrt-artifact-lint/lint.cjs` (the deterministic artifact structure lint), `scripts/vendor-skills.cjs` (the `skills/vendor/` refresh tool), and `skills/hrt-apply-code-review/floor-guard.cjs` (the apply review's diff floor guard) all have test suites, run together by `cd scripts && npm install && npm test` (`node --test merge-config.test.cjs lint.test.cjs vendor-skills.test.cjs floor-guard.test.cjs`). `lint.cjs` and `floor-guard.cjs` live in their skill folders because they ship downstream via `npx skills add`; their tests, `scripts/lint.test.cjs` and `scripts/floor-guard.test.cjs`, deliberately stay in `scripts/` so they do NOT ship — keep each pair in sync. `scripts/package.json` exists only to give `merge-config.test.cjs` a resolvable `yaml` devDependency — `lint.cjs` and `floor-guard.cjs` have zero dependencies. `scripts/node_modules/` is gitignored; `package-lock.json` is committed for reproducible test installs.

`lint.test.cjs` covers 65 cases via `node:test` (hashtag counts, scenario-as-bullet, requirement with no scenario, missing WHEN/THEN, SHALL/MUST as WARN, unknown delta header, REMOVED without Reason/Migration, capability↔spec-file both directions, non-kebab capability, missing/absent design.md section, `Covers:` target not in specs, "no new code surface" skip, archive task, non-checkbox bullet as WARN, unverified/verified External Dependencies rows, missing proposal.md section, bad-args exit 2, template-placeholder capability ignored, plus seven for the tasks.md group graph (`Depends on`), eight for the security gate (keyword with no threat entry and no skip line, a well-formed `[Threat: ...]` entry, a skip line, a malformed threat line, no keyword, a skip line beside threat entries, a one-word skip reason, everyday words like design token), nine for task coverage (`Covers:` per group in both directions, semicolon lists, `none`, case-insensitive matching, a line in an HTML comment or after the first checkbox ignored), seven for threat ids (id required and unique, a threat no group covers, an unknown id in `Covers:`, a covering group needing a `[security]` task, case-insensitive ids), eight for proposal size and shape (word ceiling, comments excluded, paragraph/bullet over 100 words, code fence, more than 5 open-question bullets, optional sections accepted, the `Size facts:` line), and three for `--phase=proposal` and bad flags). Run it after any change to `lint.cjs`. The lint is deterministic-only — the judgement calls (is a scenario genuinely behaviour, is a requirement genuinely testable) stay with the review subagents.

`merge-config.test.cjs` covers 37 cases via `node:test` (`npm test` — run it after any change to `merge-config.cjs`; a few tests use real subprocess timing/permissions and can't be simulated by reading the code). Core round-trip and refusal behavior: absent config file, config with `schema:` only (no `context:` key), existing `context:` as single-line quoted/unquoted scalar, multiline block-literal (`|`), multiline folded (`>`), null-ish forms (`context:` empty, `null`, `~`), a fully commented-out sample block, idempotent re-run, general re-parseability, a UTF-8 BOM, YAML 1.1-ambiguous barewords (`yes`/`no`/`on`/`off`) treated as strings not booleans, a merge-key-supplied `context:` (`<<: *anchor`) treated as absent since `doc.get` doesn't resolve merge keys, very long `contextText`, and markers containing regex metacharacters. Refused cleanly (non-zero exit, file untouched, no raw stack trace): `context:` as a non-string YAML node (list, mapping, or `*alias`), malformed YAML (duplicate keys, tab indentation, a multi-document `---` stream) caught via `doc.errors` right after parsing, a symlinked `configPath` (dangling or not — checked via `lstatSync` before anything else touches the path), and filesystem errors (`EISDIR`, `EACCES`, etc. — mapped to a one-line message instead of Node's default uncaught-exception dump).

Three subagents (one per angle — YAML data-shape, filesystem/OS, CLI-argument/adversarial) were run against this script to find edge cases beyond what manual review caught. Their findings became most of the tests above, plus four real bugs, all now fixed (tests prefixed `FIXED:` rather than the `KNOWN GAP:` prefix they carried while still open — keep using that convention for any newly found gap: land the test asserting current, undesirable behavior first, then flip it to desired behavior as the TDD signal to fix the script, rather than fixing blind):
- **Marker-version-drift** (real, already happened once in this repo's history per the `context:` wording change): the old `.includes(marker)` idempotency check couldn't tell "already merged" from "not yet merged," so a reworded `CONTEXT_MARKER`/`CONTEXT_TEXT` in a future installer would append a second, possibly-contradictory block forever instead of replacing the old one. Fixed by `replaceOrAppendBlock()`: an exact, line-anchored match of the marker line is searched for; if found, everything from that line through the next blank line (or end of string) is replaced wholesale; if not found, a new block is appended. This also fixed the two bugs below as a side effect, since line-anchored matching replaced substring matching.
- **Marker-as-substring false-positive idempotency**: a marker (or an accidentally near-empty one, e.g. a single space) that happened to already appear inside unrelated existing prose used to make the script treat the file as "already merged" and skip the real append, silently. Fixed by the same line-anchored match above — a marker only matches a line that equals it exactly, not any line containing it as a substring.
- **Symlinked `configPath` was followed and written through**, with no `lstat`/no-follow guard. Fixed: `fs.lstatSync` (not `fs.existsSync`, which follows symlinks and would report `false` for a dangling one, hiding it) runs before anything else touches the path; a symlink of any kind — dangling or not — is refused with a clean error.
- **Filesystem errors surfaced as raw Node stack traces**, not the script's own clean `console.error` style used for YAML-parse and non-string-context errors. Fixed: `readFileSync`/`mkdirSync`/`writeFileSync` are wrapped in try/catch, and `failWithCleanFsError()` maps common codes (`EISDIR`, `EACCES`, `EPERM`, `ENOSPC`, `ENOTDIR`) to a one-line message. Not fixed (documented, not tested — timing-dependent and not worth the complexity for a script whose caller already treats any non-zero exit as fatal): `writeFileSync` still truncates in place rather than write-temp-then-rename, so a kill mid-write could in principle leave `config.yaml` empty or partially written.

`floor-guard.test.cjs` covers 19 cases via `node:test`, each in a throwaway git repo: clean change, each Python and JS/TS suppression form, security suppression as its own rule with the line text (and any secret) never printed, suppressions in non-code files ignored, skips in an existing Python test (unittest, pytest, `skipTest`), the Odoo `'-standard'` tag versus `'-at_install'`/`'post_install'`, no flag for a skip in a test file the change creates, JS `.skip(`/`xit(` in a spec versus `cursor.skip(` in production code, a deleted test file versus `git mv` and a plain `mv`, assertions moved between files, an edited expected value, a change-wide drop (one flag with counts), a deleted test lowering the count, stubs and swallowed exceptions (Python and TS), none of those in test code or for an `except` with a body or a `TODO`, `--base` seeing committed work, untracked binaries skipped, and exit 2 for a bad argument, a non-repo, an unknown base, or a repo with no commit. Run it after any change to `floor-guard.cjs`.

One limitation was found *during* the marker-drift fix itself and deliberately left as-is rather than fixed further, per `KNOWN LIMITATION:` in both the code comment above `replaceOrAppendBlock()` and its own test: block-end is inferred from the first blank line after the marker, so a `contextText` with an internal blank line (a multi-paragraph body) only gets its first paragraph replaced on a reword — later paragraphs from the old block survive as orphaned trailing text. Not a real risk today since the installer's `CONTEXT_TEXT` is always a single line; a real fix needs an explicit block-closing delimiter, which would change the format of every already-installed `config.yaml` to solve a problem that doesn't exist yet.
